# 02 · 分工说明（客商对接智能系统 · 五人 · 各自工作区）

> 原则：**一人一目录、一人一职责、一个统一接口、最后合成一个作品。**
> 任何人只在自己的工作区提交代码；公共改动（docs、接口、根配置）走 PR 由组长合入。

## 总览表

| 成员 | 角色 | 工作区 | 一句话职责 |
|------|------|--------|-----------|
| 成员1 | 组长 · 后端 | `backend/` | 定架构、供需数据模型、API、匹配编排、连接/意向单 |
| 成员2 | 前端 | `frontend/` | 需求方端 + 供给方端 + 匹配结果展示 |
| 成员3 | AI 匹配引擎 | `ai-engine/` | 匹配打分（成本/利润/效率/兼容）+ 组合推荐 + 理由 |
| 成员4 | 数据/评测 | `data-pipeline/` | 供需样例数据 + 匹配效果评测 |
| 成员5 | 测试/部署/交付 | `deploy/` | 测试、部署、Demo、提交材料 |

## 成员1 · 组长 · 后端（backend/）

**职责**
- 定整体架构与技术选型，定义并维护 `docs/03-接口规范.md`。
- 实现 FastAPI 后端：发布需求、上架供给、匹配编排、建立连接（意向单）。
- 调用成员3 的匹配引擎、成员4 的数据服务，统一响应与错误码。
- 组织每日进度同步，合入 PR，解决跨模块阻塞。

**依赖**：无（先出接口规范）。**被依赖**：成员2/3/4 均按接口对接。

**验收标准**
- [ ] 发布需求、上架供给、匹配、建立连接 四个接口可用。
- [ ] 统一响应格式与错误码按规范实现。
- [ ] 前后端/引擎/数据真实串联，全流程可跑通。

## 成员2 · 前端（frontend/）

**职责**
- 搭 React + Vite + TypeScript 骨架。
- 需求方端：发布需求、查看匹配结果、勾选供应商。
- 供给方端：上架/管理资源与商品。
- 匹配结果与意向单展示，处理加载/错误态。

**依赖**：成员1 接口规范。**被依赖**：成员5 录 Demo。

**验收标准**
- [ ] 两端页面可操作。
- [ ] 能跑通「甲发布需求 → 看到匹配 → 勾选 a,b,e → 生成意向单」全流程。

## 成员3 · AI 匹配引擎（ai-engine/）

**职责**
- 实现匹配打分算法：成本 / 利润 / 效率 / 兼容性 四维。
- 供应商组合推荐（如整机需要的多部件组合）。
- 生成每项匹配的理由，输出标准化 JSON。

**依赖**：成员1 引擎接口约定。**被依赖**：成员1 调用、成员2 展示。

**验收标准**
- [ ] 给定需求 + 候选供给，稳定输出排序 + 打分 + 理由。
- [ ] 兼容性判断正确（如 CPU/主板匹配）。

## 成员4 · 数据/评测（data-pipeline/）

**职责**
- 设计供需数据结构。
- 准备样例数据，含演示主线「甲 + a,b,c,d,e」。
- 实现匹配效果评测（打分是否合理、排序是否正确）。

**依赖**：成员1 数据接口约定。**被依赖**：成员1 调用、成员3 验证。

**验收标准**
- [ ] 提供一套可跑通演示的供需样例数据。
- [ ] 评测脚本能评估匹配合理性并给出指标。

## 成员5 · 测试/部署/交付（deploy/）

**职责**
- 部署到知乎 AI Works（或等价平台）。
- 端到端集成测试，记录并推动修复 bug。
- 录 Demo（用甲的例子）、路演 PPT、提交材料。
- 收口 README 与 `docs/04-提交指南.md`。

**依赖**：全员。**被依赖**：最终提交。

**验收标准**
- [ ] 一键部署可用，服务可访问。
- [ ] Demo 完整展示全流程。
- [ ] 材料齐全，按时提交。

## 协作规则

1. 分支 `feature/<成员名>/<功能>`，合 `main` 走 PR。
2. 只改自己工作区；改 docs/根配置需在 PR 说明。
3. 接口变更先改 `docs/03-接口规范.md` 并通知全员。
4. 每日同步进度；阻塞超过半天立即找组长。
